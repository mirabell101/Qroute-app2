# Fare Management Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let administrators import a distance-fare CSV or manually publish an effective-dated fare rule with editable kilometre bands.

**Architecture:** A pure backend fare-management module parses/validates CSV data and manual rule payloads, then uses the verified admin request client to persist a new rule and its bands. A single Admin page loads configuration, turns a CSV into an editable draft, and publishes either draft type through the existing authenticated admin API pattern.

**Tech Stack:** React 19, TypeScript, Express 5, Supabase JS, Vitest, Tailwind.

**Spec:** `docs/superpowers/specs/2026-11-21-fare-management-design.md`

## Global Constraints

- Preserve the current schema, RLS policies, roles, and historical fare rules.
- No new dependency, remote write, commit, or push.
- Use `requireAuth` and `requireAdmin`; all fare reads/writes use the request-scoped access-token client.
- CSV is UTF-8, `.csv`, no larger than 1 MB; backend validation is authoritative.
- CSV headers are `distance_km`, `regular`, `student`, `senior_citizen`, `pwd`.

## Review Focus

- Quoted CSV values and CRLF newlines parse as intended; test parser task.
- A CSV row that cannot be regenerated by the derived formula is rejected; test service task.
- A manually edited band cannot leave a gap or overlap; test service task.
- An authenticated non-admin cannot read or publish fares; test route task.
- Quarter-peso regular and discounted values retain cents in the public fare card; test calculation task.
