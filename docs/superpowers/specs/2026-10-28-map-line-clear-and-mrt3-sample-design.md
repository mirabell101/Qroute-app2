# Map Line Clearing and MRT-3 Sample Data

## Intent

Make route paths temporary trip context: clearing a trip or tapping its current boarding point hides every route line while retaining the map, markers, and place details. Provide a reviewable SQL script that replaces the current demo transit data with a Quezon City MRT-3 segment and sourced sample fares. The script is for the user to review and run; it must not be executed against Supabase by this work.

## Goals

- Hide all displayed route polylines when the user clears a trip or taps the active boarding point again.
- Keep place/route details and stop/terminal markers visible; a later relevant map or route search selection can show route lines again.
- Replace route, route-stop, stop, terminal, and route-specific rail-fare rows in a guarded SQL transaction.
- Seed the North Avenue, Quezon Avenue, GMA Kamuning, and Araneta-Cubao MRT-3 segment, using Quezon City station coordinates sourced from OpenStreetMap.
- Seed station-pair base fares from the secondary MRT-3 fare guide and add applicable Student/PWD discounts using the existing fare model. Label fare information as secondary, not verified.
- Keep the sample route approved/visible and preserve transport reference data and general fare rules.

## Non-goals

- No live Supabase writes, credentials, or secret-file reads.
- No invented routes, station coordinates, fare amounts, or road records.
- No identity-sequence reset or changes to transport types/variants, fare areas, or general fare rules.
- No new road table; road geometry continues to be obtained by the existing route-layer behavior.
- No change to route-selection, endpoint ordering, or fare-calculation behavior beyond the requested line visibility and the sample data.

## Approaches

1. **Separate route-line visibility from trip selection (chosen).** Add an explicit visibility state so clearing endpoints does not discard the selected place, route details, or markers. Hide all polylines on clear/repeated boarding-point click; later map/search route selection makes relevant lines visible again. This matches the requested map behavior without coupling line visibility to route identity.
2. **Clear the selected route and place along with the trip.** This would also remove context the user wants to keep, so it is not chosen.
3. **Keep deriving lines from selected/visible route IDs.** This leaves lines visible after clearing a trip and does not meet the request.

For sample data, the chosen path is a SQL-only, explicitly scoped reset-and-seed script. The alternatives—executing the changes directly in Supabase or leaving the current demo records—were not selected. Fares use the base matrix and separate Student/PWD discounts, rather than the reported temporary all-rider 50% relief, because its current status and exact MRT-3 matrix were not verified.

## Interaction

- Clear trip resets boarding/destination and hides every route polyline without clearing the selected place, route details, or map markers.
- Tapping the current boarding point again resets the trip and hides the route polylines.
- Selecting a relevant stop/terminal or route through the existing map/search flow makes its route lines visible again.
- Other selection behavior remains unchanged.

## SQL data and safety

- The script must state its destructive scope and explain that there is no `roads` table to clear; route geometry is generated by the existing map flow.
- Before deleting, it must verify the expected demo dataset and abort clearly if the live rows differ, so later-added data is not silently removed.
- Delete dependent data in safe order and run the reset and seed in one transaction. Use generated IDs and existing relationships rather than resetting sequences.
- Seed one ordered MRT-3 route and its four station stops; keep train route identity separate from any road transport route.
- Seed the six unique station pairs with the base fare for their station gap, matching the source matrix. Student/PWD amounts are calculated by existing application rules, not duplicated in `rail_fares`.
- Preserve fare-rule records and add 20% Student/PWD discount rows for the rail variant, matching the currently configured discount percentage, with source/status metadata marked unverified until confirmed for this rail service.
- Mark the sample route approved/active as supported by the schema. Include source URLs, dates, and secondary verification status for the fares; document OpenStreetMap attribution for station coordinates.
- The SQL file is a deliverable for review. Validate its schema references and transaction logic locally, but do not execute it against the connected Supabase project.

## Constraints and builder decisions

- Reuse the current `Home.tsx` map state and route-layer rendering, the existing fare and route schemas, and fare-card discount logic.
- Use the existing train transport type and rail matrix variant; resolve IDs by stable identifying fields and fail if they are missing or ambiguous.
- Use the existing MRT-3 source for base station fares and OpenStreetMap station records for coordinates. Keep fare rows marked `secondary`; do not present them as officially verified.
- Do not read `.env` or other sensitive files. Supabase reads are limited to schema/reference data needed to prepare the script; no writes are authorized.
